## A2A 完整工作流梳理（代码实证，修正此前几处认知）

### 拓扑
- 主智能体 = A2A Client，同时自身是 8000 上的 A2A Server；三阶段（Planner → DAGExecutor → Synthesizer）。
- 子智能体（A2A Server，各自独立进程）：8001 网络搜索 / 8002 数据库 / 8004 向量 / 8005 长期记忆。8003 RAGFlow 注释禁用。
- 8100 MySQL MCP Server 是**数据库子智能体的工具依赖**，不是 A2A 节点。
- `start_services.py` 用 uv 起 7 个进程（含 8100 MCP 与后台异步摘要 agent，后者无端口）。
- 每个子智能体内核 = `deepagents.create_deep_agent(model, system_prompt, tools, skills, checkpointer=InMemorySaver)`。

### 修正此前的认知
- `RECURSION_LIMIT = 15`（早期记成 22，错）。
- 子 agent 服务端有**重试**：`MAX_ATTEMPTS = 2`，且仅当 code==ERROR 才重试；每次 attempt 用**独立 thread_id** `f"{task_id}#{attempt}"`（不重试 MISS，因为 MISS 是"正常无结果"）。
- DataPart 现携带 `{code, content, usage, score}`（早期只有 code/content）。
- **长期记忆召回不走 A2A**：`memory_client.recall_memories` 直接本地 `asyncio.to_thread(recall_memory, ...)`（dense+rerank+阈值+时间衰减+来源多样性）。只有**提取**走 A2A（`call_memory_agent` + request metadata 带 user_id），且 fire-and-forget。

### 关键链路
1. 发现：`ClientFactory.create_from_url(base)` 先拉 `GET /.well-known/agent-card.json`（`_build_agent_card`：skills = 工具列表，JSONRPC binding）。
2. 调用：`_call_subagent` → `new_text_message(query)` → `SendMessageRequest` → 非流式 `client.send_message`，超时 120s；只传 query，不传 task_id → 服务端每次新 uuid。
3. 服务端：`_A2AAgentExecutor.execute` → `set_request_metadata(context.metadata)` + `begin_request()` → `agent.ainvoke(..., thread_id=task_id#attempt, recursion_limit=15)`，超时 110s（刻意 < 客户端 120）。
4. 结果提取 `_extract_result_from_messages` 三级优先：最终 AI 显式信封 > 最后工具信封 > **ERROR 兜底（绝不默认 HIT）**。
5. 回传双通道：text part（正文）+ data part（`{code,content,usage,score}`）；客户端 `add_usage(data["usage"])` 把子进程用量归并进主请求累计器。
6. 编排消费：executor `parse_result` → results/codes/scores；`fallback_for` 步骤按 `needs_fallback(MISS|ERROR)` 决定是否执行；`asyncio.gather(return_exceptions=True)` 运行期不中断；每批 `on_batch_done` 落 checkpoint。

## 向量检索索引的事实澄清
- dense 召回层 = ChromaDB 默认索引 = **HNSW（hnswlib）**；`get_or_create_collection(name)` **未传 metadata** → 用 Chroma 默认参数（space=l2 / M=16 / construction_ef=100 / search_ef=10，随版本略有差异）。
- **未显式设 `hnsw:space="cosine"`**，用的是默认 L2；若 embedding 未归一化则与直觉的 cosine 不一致（潜在坑）。
- 写入时是 `collection.add(embeddings=...)` —— 外部 Embedding（text-embedding-v4）自己算向量，**没用 Chroma 内置 embedding function**。
- **整条检索管线 ≠ HNSW**：dense(HNSW 粗排) + 自实现 BM25（`keyword_search` 全量内存扫描、O(N)，仅适合小库）+ RRF(k=60) 融合 + BGE cross-encoder 精排 + 50:50 归一化加权。
- `long_term_memory` 集合同样走 Chroma → 也是 HNSW。

## 文档入库管线（vector_search）
- 入口两条：① 离线 CLI `ingest_data.py`（`ingest_file`/`ingest_directory`）；② 在线工具 `ingest_document`（LLM 可调，走 `ingest_text`）。
- 管线：`_read_file`（按扩展名：pdf→pypdf 逐页 extract_text；txt/md/yml/json/csv→直接读；docx→python-docx 段落）→ `_split_text`（`RecursiveCharacterTextSplitter`，chunk_size=800/overlap=150，**中英双语分隔符** `["\n\n","\n","。","！","？","；",". ","! ","? "," ",""]`，keep_separator=True）→ `vector_store.add_chunks`。
- 向量化 `embedding.py`：OpenAI 兼容 Embedding（`text-embedding-v4`），**批大小 10**（阿里百炼限制），每条**截断 8000 字符**。
- **已知缺陷**：`add_chunks` 的 id = `f"{collection}_{i}_{hash(t[:40])}"`，用 Python 内置 `hash()`（进程间不稳定）+ 只看前 40 字符 → **重复入库产生重复块而非覆盖**；知识库文件入库走 `add`（不幂等），只有长期记忆走 `upsert_chunks`（覆盖）。PDF 无 OCR/无版面；ingest 无业务元数据（时间/类别）；`ingest_directory` 串行且失败只标 -1 不报错。

## "Task" 概念澄清（项目里有三个同名 task）
1. **A2A 协议原生 Task**（带生命周期 + TaskStore）：**基本没落地**。`build_app` 里 new 了 `InMemoryTaskStore()` 但从不产生/更新 Task——`_A2AAgentExecutor.execute` 只 `enqueue_event(new_message(...))` 返回一条 **Message**（即时响应工作流）；`cancel()` 空实现；没有 tasks/get、TaskState、流式 TaskStatusUpdateEvent。
2. **业务层 task/session**（`agents/orchestrator/server.py`）：前端 `POST /api/task` 带 `thread_id`（无则 uuid4），后台 `asyncio.create_task(run_deep_agent)`，用 `active_tasks: dict[str, asyncio.Task]` 跟踪 + `/ws/{thread_id}` 推送 + session 表 + checkpoint。这里的 `asyncio.Task` 是 **Python 协程任务**，与 A2A Task 无关（纯命名撞车）。
3. **A2A 消息层的 `task_id`/`context_id` 字段**：客户端 `a2a_tools` 只构造 message、**从不传 task_id** → 服务端 `task_id = context.task_id or uuid4()` 每次新生成；唯一用途是拼 LangGraph checkpointer 的 `thread_id = f"{task_id}#{attempt}"` 并回填返回消息（客户端也不读）。→ 子 agent 从 A2A 视角是**无状态一次性调用**，无法多轮续接。
