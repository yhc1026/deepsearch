## 面试式深挖：三个核心子 Agent 的工具清单（供后续复用）

对话场景：用户以面试官身份对项目做技术深挖，本轮问"数据库 / 向量库 / 网络搜索三个 subagent 各持有哪些工具"。

### 工具清单（代码实证）
- **网络搜索 Agent（8001）** — 1 个工具
  - `internet_search(query, topic, max_results=5, include_raw_content=False)` → Tavily；内部把每条 `content`/`raw_content` 截断到 **300 字符**（`tavily_tool.py`）。
- **数据库 Agent（8002）** — 6 个工具 = 3 MCP + 3 兜底（功能重复）
  - MCP（`mcp_tools.yaml`，Streamable HTTP，30s 热插拔）：`mysql_list_tables`、`mysql_get_schema`(LIMIT 100)、`mysql_execute`(任意只读 SQL)
  - 兜底（`db_tools.py` 直连）：`list_sql_tables`、`get_table_data`(LIMIT 100)、`execute_sql_query`(任意 SQL)
  - system_prompt 显式注入"优先 MCP，复杂 SQL 才回退兜底"策略。
- **向量库 Agent（8004）** — 3 个工具
  - `search_knowledge_base(query, collection="default")`：核心；3 个 query 变体 × hybrid(dense+BM25 RRF) → 去重(前200字符指纹) → BGE rerank → 阈值 0.3 门控 → top3，每条截断 **600 字符**。
  - `list_collections()`、`ingest_document(content, collection, source_name)`（分块 800/150 写入 ChromaDB）

### 关键观察（token 风险相关）
- 只有数据库的 `execute_sql_query` / `mysql_execute` **无结果字符上限** → 是"简单问题吃海量 token"的头号嫌疑。
- 三个 Agent 输出尺寸契约不统一：网络 5×300、向量 3×600 都有封顶，数据库裸奔。
- 数据库 Agent 每次调用都在 prompt 里带 **6 份工具 schema**（3+3 同义），既增加选择负担也多耗 schema token。
- 向量 Agent 是唯一"工具内部再调 LLM"的（query 变体生成，`add_usage` 计入请求累计器）。

### 提出的工具扩展方向（设计讨论结论）
- 网络搜索（仅 1 工具、结果截断 300 字）：补 `fetch_url`（Tavily extract 取正文）、`search_on_site`（限定域名）。
- 数据库（缺元信息与护栏）：补 `describe_table`（DESCRIBE/information_schema 取列类型再拉数据）、`count_rows`、`explain_query`；给 `execute_sql_query` 加 LIMIT 注入 + max_chars + 只读白名单（当前它能跑 DML/DDL）。
- 向量库（管杀不管埋）：补 `delete_document`、`list_documents`、给检索加 metadata where 过滤（按来源/时间）。
- 原则：加工具要闭合"能力环 + 风险约束"，且每加一个都在全局 schema token 与模型选择负担上有成本，能并参则并参。

### 会话背景
- 之前几轮已讨论：模型选型、A2A 机制、JSON 容错、长期记忆、异步压缩、断点重放、以及"input 40000 / output 几百"的 token 排查方法论。
- 用户偏好：**尽量纯文字回复，未要求就不要画图**。
