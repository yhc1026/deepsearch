# Main Agent 决策纠偏技术文档

## 问题描述

Main Agent（主智能体，port 8000）作为任务编排者，需根据用户问题将任务路由到三个远程专家工具之一：

- `call_ragflow_query` → RAGFlow 内部知识库（行业研报、市场分析等）
- `call_database_query` → MySQL 结构化业务数据
- `call_network_search` → Tavily 互联网公开信息

**实际表现：** Main Agent 过度倾向调用 `call_network_search`，即使某些问题在 RAGFlow 内部知识库中已有高质量的现成答案（如电商行业趋势、金融政策分析等），仍然选择了互联网搜索。

## 根因分析

问题出在 `app/prompt/prompts.yml` 中的提示词设计，四个层面的偏差叠加导致 LLM 系统性偏向 Tavily：

### 1. 工具定位不对称（核心原因）

```
# 改前 — L34-36
1. call_database_query: 企业结构化数据库查询（药品/库存/销售记录）
2. call_ragflow_query: 企业内部知识库检索（PDF/白皮书/研报/制度文件）
3. call_network_search: 互联网公开信息检索（新闻/政策/趋势/天气/百科/网页）
```

- Tavily 覆盖 "新闻、政策、趋势、天气、百科、网页" — **极其宽泛，几乎无所不包**
- RAGFlow 被限定为 "PDF/白皮书/研报/制度文件" — **听起来像查公司制度**
- 当用户问 "电商行业有什么趋势"，LLM 看到 "趋势" 天然匹配 Tavily 的领域描述

### 2. 决策树按关键词匹配，而非领域优先

```
# 改前 — L47-49
- 需要公开信息（新闻/政策/百科/天气）→ 调用 call_network_search
- 需要业务数据（药品/库存/销售）→ 调用 call_database_query
- 需要内部文档（研报/制度/白皮书）→ 调用 call_ragflow_query
```

关键词 "趋势" 在重写规则 (L27) 中属于网络搜索范畴，直接触发 Tavily，RAGFlow 从不会被考虑。

### 3. Main Agent 缺少知识库自感知能力

LLM 调用 `call_ragflow_query` 之前，不知道 RAGFlow 中实际有哪些知识库。没有 "RAGFlow 包含电商行业分析和金融行业研究" 这种前置信息，LLM 只能靠工具描述猜测，倾向选择更 "安全" 的 Tavily。

### 4. 子 Agent description 强化了偏差

RAGFlow 子 Agent 的 description（LLM 选工具时看到的 "名片"）：

```
# 改前
负责查询 RAGFlow 内部知识库中的非结构化文档信息，例如 PDF、白皮书、研报、制度文件...
当任务需要查询企业内部私有文档...时，使用此助手。
```

"企业内部私有文档" 让 LLM 以为 RAGFlow = 规章制度查询，即使知识库实际包含行业研究报告，也不会被优先考虑。

## 修改方案

以下修改均在 `app/prompt/prompts.yml` 中完成，不涉及代码逻辑变更。

### 改动 1：主 Agent 工具列表 — 重新定义每个工具的定位与边界

```yaml
# 改后 — L32-37
【你掌握的工具】
远程专家工具（信息获取）：
  1. call_database_query(query): 企业结构化数据库查询（药品/库存/销售记录）
  2. call_ragflow_query(query): 企业内部知识库检索，覆盖行业研报、市场分析、政策解读、
     产品资料、制度文件等专业知识。这是你获取高质量行业洞察的首选来源。
  3. call_network_search(query): 互联网公开信息检索（实时新闻/天气/百科/网页）。
     仅用于内部知识库和数据库无法覆盖的补充查询。
【路由优先级】对于任何涉及行业分析、市场研究、政策解读、专业领域知识的问题，
  务必先调用 call_ragflow_query。只有当 RAGFlow 返回"匹配度过低"或无相关知识库时，
  才使用 call_network_search 作为后备。
```

**关键变化：**
- RAGFlow 从 "查文档工具" 升级为 "行业洞察首选来源"
- Tavily 从 "万能搜索" 明确降级为 "补充查询" 和 "后备"
- 新增显式【路由优先级】规则，明确 RAGFlow first 原则
- 工具列表排序也调整为 DB → RAGFlow → Tavily，暗示优先级

### 改动 2：工作流程决策树 — 从关键词匹配改为优先级决策

```yaml
# 改后 — L45-52
【工作流程】
第一步：分析用户问题，确定需要哪些信息来源（按优先级决策）
  1. 涉及行业分析、市场趋势、政策解读、专业知识 → 优先调用 call_ragflow_query
  2. 涉及药品/库存/销售等具体业务数据 → 调用 call_database_query
  3. 涉及实时新闻、天气查询、最新事件等时效性强的公开信息 → 调用 call_network_search
  4. 内部知识库或数据库返回"匹配度过低"时 → 用 call_network_search 补充
  5. 复杂问题不确定信息来源时 → call_ragflow_query 与 call_network_search 并行调用，综合对比
  6. 可以多次调用同一工具，从不同角度获取信息
```

**关键变化：**
- 从 "按信息类型匹配关键词" 改为 "按领域做优先级决策"
- RAGFlow 排第 1 位，DB 第 2，Tavily 第 3
- 新增 "匹配度过低" 的 fallback 链路（规则 4）
- 新增 "不确定时并行调用" 作为兜底策略（规则 5）

### 改动 3：RAGFlow 子 Agent description — 扩展定义域

```yaml
# 改后 — L111-115
name: "RAGFlow助手"
description: |
  负责查询 RAGFlow 内部知识库中的专业领域知识，覆盖行业研报、市场分析、政策解读、
  产品资料、制度文件等内容。
  当任务涉及行业趋势、市场研究、专业知识问答时，应优先使用此助手。
  只有当知识库明确返回"匹配度过低"时，才改用网络搜索助手。
```

**关键变化：**
- "非结构化文档信息" → "专业领域知识"
- "企业内部私有文档" → 明确列出行业趋势/市场研究/专业知识问答
- 新增降级条件："匹配度过低"时改用网络搜索（与子 Agent system_prompt 中已有的返回格式对齐）

### 改动 4：Tavily 子 Agent description — 明确边界与降级定位

```yaml
# 改后 — L82-85
name: "网络搜索助手"
description: |
  负责从互联网检索公开信息的助手。仅用于补充内部知识库和数据库无法覆盖的内容。
  适用场景：实时新闻、天气、百科查询、最新事件。
  不适用场景：行业分析、市场研究、政策解读（这些应由 RAGFlow 助手处理）。
  优先使用 RAGFlow 和数据库查询，本助手作为后备。
```

**关键变化：**
- 新增 "仅用于补充" 和 "后备" 定位
- 新增 "不适用场景" 划清边界
- 明确标注 "优先使用 RAGFlow 和数据库查询"

## 纠偏逻辑全景

```
用户问题
    │
    ▼
┌─────────────────────────────────────────────┐
│ Main Agent 路由决策                           │
│                                               │
│ 三层信息同时影响 LLM 的工具选择：               │
│                                               │
│ ① 主 prompt 工作流程（改动1、2）               │
│    决策树第一行就是 RAGFlow                    │
│                                               │
│ ② 工具 docstring（改前：a2a_agent_tools.py）   │
│    call_ragflow_query 的适用场景已从            │
│    "PDF/白皮书" 扩展为 "行业洞察首选来源"       │
│                                               │
│ ③ 子 Agent description（改动3、4）             │
│    RAGFlow 的"名片"从文档查询变成了专业知识查询  │
│    Tavily 的"名片"标注为后备                   │
└─────────────────────────────────────────────┘
    │
    ▼
  优先 call_ragflow_query
    │
    ├── 有匹配 ──→ 使用知识库结果
    │
    └── "匹配度过低" ──→ fallback call_network_search
```

## 局限性

1. **知识库不可见问题未根本解决。** Main Agent 仍然不预先知道 RAGFlow 中有哪些知识库。未来可考虑在 Main Agent 启动时或会话初始化时，注入 RAGFlow 当前可用知识库的摘要信息，让路由决策更精准。

2. **"匹配度过低" 依赖子 Agent 的返回格式。** 当前 RAGFlow 子 Agent 返回该提示的条件是 `get_assistant_list` 返回空或助手不匹配。如果助手存在但回答质量差，不会触发此降级逻辑。

3. **提示词修正本质是概率性的。** LLM 路由决策仍是基于 prompt 的概率行为，不是确定性规则。极端情况下仍可能出现路由错误，后续可考虑引入结构化路由（如 function-call 级别的路由中间件）。

## 影响范围

- 文件：`app/prompt/prompts.yml`
- 不涉及代码逻辑、API 接口、数据库结构变更
- 不影响子 Agent 服务的独立运行
- 修改即时生效，无需重启（每次 LLM 调用读取最新 prompt）
